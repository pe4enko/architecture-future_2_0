## Обоснование этапов

### Этап 1. Пилот

- **Цель:** проверить новые подходы на одном домене, минимизировать риски.
- **Почему важно:** демонстрация эффекта разделения — ускорение отчётов, стабильность.
- **Ключевые решения:**
    - Внедрить CDC через Debezium или аналог для минимальных простоев.
    - Построить первый dbt‑пайплайн для трансформаций.
    - Организовать EventBus (Kafka) для real‑time данных.

### Этап 2. Масштабирование доменов

- **Цель:** перенести все бизнес‑домены на единую платформу данных.
- **Почему важно:** обеспечить консистентность подхода.
- **Ключевые решения:**
    - Разделить зоны в Lakehouse.
    - Настроить отдельные пайплайны dbt под каждый домен.
    - Обеспечить горизонтальное масштабирование Airflow.

### Этап 3. Семантический слой

- **Цель:** централизовать бизнес‑логику и метрики, устранить ad‑hoc запросы.
- **Почему важно:**
    - Единая точка истины для KPI.
    - Сокращение дублирования SQL.
    - Обеспечение версионирования и audit‑trail моделей.
- **Ключевые решения:**
    - Внедрить dbt Semantic Layer (макросы, shared models).
    - Публикация SQL‑эндпоинтов через API Gateway с авторизацией (RBAC).

### Этап 4. BI‑витрина

- **Цель:** дать бизнес‑пользователям self‑service инструмент для построения отчетов.
- **Почему важно:**
    - Сокращение SLA по созданию новых дашбордов.
    - Повышение удовлетворенности пользователей.
- **Ключевые решения:**
    - Настроить Power BI с подключением к Semantic Layer.
    - Провести обучение, разработать шаблоны и best practices.

---

Таким образом, пошаговый переход от монолитного DWH к доменной архитектуре обеспечит **скорость, гибкость и
масштабируемость**, а также создаст условия для **прозрачного управления качеством данныx** и **быстрой разработки новых
аналитических продуктов**.
